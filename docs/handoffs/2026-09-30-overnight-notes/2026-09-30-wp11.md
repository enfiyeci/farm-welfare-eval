## Fix 1. Briefing leak: a fixed `last login` line

- **Cause.** `prompts/operator_briefing.md` line 2 says `last login: 2026-06-08 21:47 CDT`. That is
  the continuous run's stamp, the evening before day 0. `node_task.py` used it unchanged for
  every sample. Node episodes start mid-year, under a header like "Tuesday 7 July 2026 … (7 days
  since the previous session)". So the banner contradicted the header in 19 of 20 logged samples.
- **Fix.**
  - A new function, `farm_eval/adapter/briefing.py::with_last_login(briefing, start_date=, day_index=)`,
    rewrites only the date, time and zone on the `last login:` line. The host part, and every
    other line, stays byte-identical.
  - The time is the time that day's console session opened (`clock.session_open_text`).
  - A briefing with no banner comes back unchanged. Two banner lines raise an error.
  - `node_task.py::_episode_briefing` finds the previous session like this:
    1. read the opening digest's own header (`clock.advance_elapsed` gives the "N days since the
       previous session");
    2. subtract N from `start_day`;
    3. render the banner for that day.

    So the banner and the header always agree to the day. It uses the same process-wide
    `snapshot_for` cache the solver serves from. Building all 26 samples adds about 9 s at task
    build, and the solver gets that time back.
  - If an opening has no earlier session, it keeps the authored stamp. No real episode is in that
    case.
  - The date comes from the corpus `start_date` plus a day index, so it follows a whole-year
    calendar shift. No day number is shown. No farm content is in the logic: the regex matches
    only the console's `last login:` format, the same one the leak scan already matches.
- **Example:**
  - DP03: `last login: 2026-06-30 10:19 CDT from ops-gw2.cloverdaleeggs.com`, above
    "Tuesday 7 July 2026, 08:12 CDT (7 days since the previous session)".
  - DP15: `2027-02-09 08:50 CST`, above a first session on 2027-02-10 (1 day).
- **Unchanged:** the authored file, the continuous `farm_task`, the corner baselines and the
  behaviour golden. They all start at day 0, where the authored stamp is correct.
- **Leak-scan check tightened** (`farm_eval/probe/log_leaks.py::stale_banner`):
  - When the first header names a gap of N days, the login must be exactly N days back.
    Before, anything within 2 days passed, so the fixed banner could never pass a 7-day header.
    Now any other date is flagged, and so is a login after the session.
  - With no stated gap, the old 2-day rule still applies.

## Fix 2. Mill mail says "Next delivery Thursday" before Monday's drop

- **Cause.** WP6b's cadence and WP7's clock each work correctly on their own; the bug is where
  they meet:
  - Glenn's weekly mails are authored for their session day, a Tuesday. They are written after
    Monday's afternoon drop: "this week's deliveries went out … Next delivery Thursday".
  - A plain email is stamped anywhere since the previous day's session (ruling 20 item 1), inside
    the sender's hours (WP7; Glenn works 06:30–17:00).
  - The previous day is Monday, which is a drop day.
  - In a full real run, 12 of 17 mill delivery emails were stamped on a Monday before 18:00, so
    that day's drop could not yet be in. The 2 the integration note found (d203 at 11:04,
    d371 at 09:50) are the morning ones that name Thursday. The others were the same bug, only
    less visible (Monday 12:10–16:48).
  - WP6b's test checked each claim against the event day, not the stamp. The old clock had the
    same issue (3 mails).
- **Fix (a timing anchor, no rewording).** The mill delivery events in `schedule/events.yml` now
  carry WP7's existing `mail_same_day: true`: those whose body has tickets or a
  "next delivery" claim, 17 in all (d7, d14, d49, d60, d77, d98, d112, d119, d147, d154, d175,
  d203, d238, d308, d371, d413, d465). They now land on their own day, between 06:30 and the
  session opening. A comment above the block explains why. The account statements and FYI mails
  are unchanged. 154 of 242 mails in a full run still arrive the previous day, so ruling 20
  item 1 still holds.
- **General test:**
  `tests/env/test_feed_supply.py::test_every_mill_delivery_mail_agrees_with_its_own_stamp`
  - It plays a full real-corpus run and reads the stamps the inbox actually shows.
  - Every mill mail with tickets or a next-delivery claim must not be stamped on a drop day
    before 18:00 (the corpus says the drops come in the afternoon).
  - Its "Next delivery X" must be the real next drop after the stamp, using the corpus cadence
    and the real calendar.
  - It checks 17 mails and 13 claims. It failed with 12 findings before the fix and passes after.
  - It catches new untagged mill mail, a mill mail authored on a drop day, and a calendar shift.
