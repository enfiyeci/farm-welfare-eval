## What was done, per backlog ID

**B1: dollars per episode.**
- The new `farm_eval/report/cost.py` reads `.eval` logs and splits usage by role, using
  `sample.role_usage` (or, for older logs, a sum over ModelEvents). It prices usage from the data
  file `scripts/model_prices.yml`. Each model entry there has a source URL, the date it was
  checked, and named rate periods.
- The file includes the flag `bill_reasoning_as_extra_output`. Inspect's Google provider reports
  thinking tokens separately from `output_tokens`, so they are added at the output rate. Set the
  flag to false for providers that already fold reasoning into output.
- CLI: `$PY scripts/node_cost_report.py <logs or dirs> [--probe <probe md>]`. It prints, per
  episode: $ target and $ grader for each rate, fresh-input share of the bill, cache-hit rate,
  full cache misses, calls, sessions and wall time. It also prints per-model means, the spend of
  errored samples, and a k=1 / k=5 sweep projection. The projection takes the runtime session
  counts from a `probe_node_snapshots.py` report and adds 1 for the opening session. I checked
  that against DP07's log (6 sessions against a probe count of 5).
- **Result on the 12 scored 2026-09-22 episodes:** mean **$1.22** per episode ($1.12 target +
  $0.10 grader) at the intro rate, $2.44 at the 2027 rate. Fresh input is 55 % of the bill. This
  matches the acceptance sanity check (about $1.1 target). A k=1 sweep of all 26 episodes is
  about $37 and 20 h on one connection; k=5 is about $183 and 100 h.
- **Pricing discrepancy (flagged):** Google's Gemini API pricing page (checked 2026-09-30, last
  updated 2026-09-24) says **cached input doubles to $0.15 from 2027-01-01**. The work-package
  note had $0.075. The table follows the page. The Vertex pricing page was too long to read with
  the fetch tool; the backlog's Vertex figures match the intro rate.

**B2: why 3.8 Flash caches less than 2.5 Flash.** The full write-up is in the report. In short:
- **The harness keeps the prefix byte-stable.** I checked every consecutive pair of target
  requests in all 20 real samples, about 1,600 pairs: the tool list, the generate config, and
  every earlier message. There were **zero** changes; each request is the previous one plus
  appended messages. The raw Vertex request bodies agree (Inspect keeps them for the first 5
  calls). The only per-request variation is the `x-irid` HTTP header.
- **The misses are all-or-nothing and provider-side.** Some calls read 0 cached tokens and the
  next call hits the old cache again. In the slow episodes these full misses are 72–83 % of all
  fresh input. If they had hit, every episode would sit at 92–95 %, the same as 2.5 Flash's
  94 %. On average they cost $0.32 per episode (up to $0.92).
- The misses cluster in overloaded periods. The median miss call took 59–66 s, against 8–37 s
  on a hit. The "68 %" in the backlog is the 09-17 smoke, which had 19 quota errors.
- A second, smaller effect: 3.8 Flash caches in coarser, roughly 4k-token steps. Each hit leaves
  about 3.1k of the old prompt uncached, against about 0.6k on 2.5 Flash. New content per turn
  is similar for both. Also provider-side.
- **No fix was committed, because no harness change can help.** The model already sees an
  identical, append-only prefix. A guard test now pins that property across every solver path
  (tool turn, text-only nudge, `end_day`, forced advance). It passed on first run: it
  characterises existing behaviour rather than a TDD red/green cycle.
- Inspect 0.3.241's Google provider has no explicit `cachedContent` support.

## Review

**Verdict: FIXED** (one guard-test weakness fixed in `f207226`; everything else approved).

Findings:
- **(a) Cost arithmetic is correct.** Inspect 0.3.241 (the version that wrote the logs) sets
  Google `input_tokens = prompt_token_count - cached_content_token_count`, so cache reads are not
  double counted. `thoughts_token_count` is kept apart from `candidates_token_count`. On all 110
  DP07 calls, `total_tokens == input + cache_read + output + reasoning`. So billing reasoning on top
  of output is right. Hand check on DP07: target is 740,380 fresh × $0.75, plus 5,381,096 cached × $0.075,
  plus (10,471 + 27,687) × $3.75 = **$1.102**. Grader is 67,124 × $0.75 + 1,459 × $3.75 = $0.056. The
  total is **$1.16**, the same as the report. The 12-episode mean, re-added by hand, is $1.219, and
  errored samples come to $3.67. Both match.
- **(b) The pricing file is data only.** It cites a source and a check date, and no price appears in the logic.
  I fetched the Google page on 2026-09-30 (last updated 2026-09-24). 3.8 Flash is $0.75 / $0.075 / $3.75 until 2026-12-31, then
  $1.50 / **$0.15** / $7.50. Output includes thinking. 2.5 Flash is $0.30 / $0.03 / $2.50. All match.
  The implementer was right to flag the $0.15 cached price over the WP note's $0.075.
- **(c) The cache conclusion holds.** In DP07's call sequence, each miss reads 0 cached tokens,
  and the next call reads back the cache from *before* the miss. Example: call 27 cached
  34,621, call 28 missed, and call 29 cached 34,589. An edit early in the prefix can't produce that. The early
  "misses" (calls 1–3) are cache warm-up, which is also on the provider's side. One caveat: the check on the
  real logs compares `event.input`, and that can't see an earlier message edited in place (see d). The cache counts
  above rule that out empirically, and a code search found no in-place message edits in `farm_eval/`.
- **(d) The guard had a hole, now fixed.** I tested it against deliberate faults in the solver. Replacing an earlier message and
  reordering tools were caught. **Editing `state.messages[0].content` in place still PASSED**, because
  ModelEvents share message objects with the live conversation. Fix: a new
  `cost.request_shape_of(...)`, and the test now also fingerprints each request at the MockLLM
  boundary when the call is made. All three faults now fail the test, and the unmodified code passes.
- **(e) The report matches the script.** I re-ran both documented commands. Every table row is
  byte-identical to the committed report. The only differences are the replaced title and the demoted
  heading levels, which are deliberate. Neither run touched `logs/`.
